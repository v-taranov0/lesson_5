# Домашнее задание к уроку №5. Первое приложение на FastAPI

Каталог товаров кофейни, который мы собирали на уроке, был складским. В нём мы регистрировали позиции вроде «кофе в зёрнах», «чай улун» и «какао-порошок», то есть сырьё и запасы, по которым продуктовая команда и мобильное приложение закупок понимают, что и в каком количестве есть на складе.

Обычный клиент кофейни этот каталог никогда не видит и ничего по нему не заказывает. Он заказывает готовый напиток — латте, капучино, какао на молоке. Именно с этой, другой стороной прилавка, сегодня и работает бариста.

Сейчас в кофейне заказы записывают на бумажных стикерах, и в загруженной точке стикеры теряются и путаются. Тимлид, который отвечает за кассовый модуль, пишет тебе:

> Нужен маленький сервис учёта заказов для одной точки. Бариста должен вбить новый заказ, посмотреть список текущих заказов, отметить заказ готовым, а если что-то пошло не так — отменить заказ. Ничего сложного, база данных и авторизация не нужны, это отдельная история. Сделай пока на том, что уже умеешь.

## Что нужно сделать

Реализуй сервис учёта заказов кофейни на FastAPI. Сервис работает с одним ресурсом — заказом (order) — и предоставляет следующие возможности.

### Создание заказа

- Эндпоинт `POST /orders` принимает название напитка, размер, количество и, опционально, имя клиента.
- Каждому новому заказу присваивается идентификатор, статус «В ожидании» (`pending`) и метка времени создания.
- Данные хранятся в памяти приложения (список или словарь) — подключать базу данных не нужно, это тема одного из следующих уроков.

### Просмотр заказов

- Эндпоинт `GET /orders` возвращает список заказов.
- Поддерживается необязательный фильтр по статусу заказа.
- Поддерживается постраничная выдача через параметры `limit` и `offset` с разумными значениями по умолчанию.
- Эндпоинт `GET /orders/{order_id}` возвращает один заказ по идентификатору. Если заказа с таким идентификатором нет — клиент получает статус 404 с понятным сообщением.

### Изменение заказа

- Эндпоинт `PATCH /orders/{order_id}` позволяет частично обновить заказ: например, изменить статус на «Готов» (`ready`) или «Выполнен» (`completed`), поправить количество или имя клиента.
- Обновлять можно только те поля, которые прислал клиент, — остальные не должны затираться.
- Если заказа с таким идентификатором нет — статус 404.

### Отмена заказа

- Эндпоинт `DELETE /orders/{order_id}` удаляет заказ из списка.
- Успешная отмена возвращает статус 204 без тела ответа.
- Если заказа с таким идентификатором нет — статус 404.

### Сервисные эндпоинты

- Эндпоинт `GET /` возвращает приветственное сообщение сервиса.
- Эндпоинт `GET /info` возвращает название сервиса и текущее количество заказов в памяти.
- Название сервиса и значения по умолчанию для постраничной выдачи берутся из настроек приложения (`.env` и `pydantic-settings`), а не зашиты в коде напрямую.
- Настройки попадают в эндпоинт через внедрение зависимостей (`Depends`), а не через прямой импорт объекта настроек в функцию.

### Модели данных

- Опиши отдельные Pydantic-модели для создания заказа, для частичного обновления заказа и для заказа, отдаваемого в ответ, — по аналогии с `ProductCreate` и `Product` из урока.
- Используй `Field` для ограничений: название напитка не должно быть пустым, количество — положительное число.
- Размер напитка и статус заказа должны быть ограничены заранее известным набором значений, а не просто произвольной строкой.
- Добавь в модель заказа поле `created_at` типа `datetime`, которое проставляется автоматически в момент создания (`datetime.now()`) — клиент его не присылает.

### Документация

- Все эндпоинты должны быть доступны и корректно протестированы через `/docs` без дополнительных инструментов вроде Postman.
- Сгруппируй эндпоинты через `tags`: `tags=["Заказы"]` на всех эндпоинтах заказов и отдельный тег, например `"Сервис"`, для `/` и `/info`.
- Добавь каждому эндпоинту `summary="..."` — короткое описание вместо имени функции в списке `/docs`.
- Заполни метаданные приложения: `FastAPI(title=..., description=..., version="1.0.0")` — полноценную шапку вместо голого названия.
- Добавь ключевым полям моделей `Field(description=..., examples=[...])` — например, у поля с названием напитка подсказку «Название напитка из меню».

## Дополнительные материалы

**Про размер напитка и статус заказа.** В уроке мы работали с обычными типами `str`, `int`, `bool`. Для набора заранее известных значений в Python есть стандартный инструмент `Enum` (`from enum import Enum`), который FastAPI понимает «из коробки»: достаточно унаследовать класс от `str` и `Enum` и использовать его как тип поля или параметра. FastAPI отклонит любое значение вне списка, а для Query- и Path-параметров ещё и покажет в `/docs` выпадающий список.

**Про `created_at: datetime`.** Это модуль стандартной библиотеки, Pydantic понимает его «из коробки» и без единого нового концепта. Заказу очень идёт метка времени: пригодится и для отладки, и для будущей сортировки.

## Бонус

Необязательные пункты для тех, кто хочет усложнить себе задачу (их невыполнение не влияет на оценку по основному рубрикатору):

- **Сортировка списка заказов:** добавь в `GET /orders` параметр `sort_by` (например, `created_at` или `drink`), который меняет порядок элементов в списке перед выдачей.
- **Ограничение параметра `limit`:** в уроке мы задавали значения по умолчанию простым способом (`limit: int = 10`), но такой параметр не ограничен сверху — его можно передать хоть миллион, и код такое значение примет. Чтобы добавить границы (например, `limit` не больше 100), у FastAPI есть функции `Query()` и `Path()` — они работают с параметрами запроса и пути так же, как `Field()` работает с полями Pydantic-модели. Почитать: официальная документация FastAPI, разделы [Query Parameters and String Validations](https://fastapi.tiangolo.com/tutorial/query-params-str-validations/) и [Path Parameters and Numeric Validations](https://fastapi.tiangolo.com/tutorial/path-params-numeric-validations/).

## Примечания

- Для `DELETE` возвращай именно `Response(status_code=status.HTTP_204_NO_CONTENT)`, а не просто `None` и не словарь — иначе клиент может получить непустое тело там, где его быть не должно.
- В `OrderUpdate` значение по умолчанию `None` у поля означает не «поле обязательно и равно `None`», а «поле не прислали, не трогаем его при обновлении». Случаи целенаправленного обнуления поля сейчас не рассматриваем. Подсказка: у `model_dump()` есть параметр `exclude_unset=True` — он оставляет только те поля, которые клиент действительно прислал.
- Если заказ не найден, используй `HTTPException`, как делали в уроке, а не словарь с полем `error`.
- Поле `created_at` достаточно объявить как `datetime` — Pydantic сам поймёт этот тип из стандартной библиотеки (без дополнительных настроек и импортов сверх `from datetime import datetime`).
- Идентификатор нового заказа не должен повторяться — даже после того, как часть заказов удалили. Подумай, почему способ `len(orders) + 1` из урока здесь уже не подходит.

## Пример

**Создание заказа.** Запрос:

```http
POST /orders

{
  "drink": "Латте",
  "size": "medium",
  "quantity": 2,
  "customer_name": "Ирина"
}
```

Ответ (статус 201):

```json
{
  "id": 1,
  "drink": "Латте",
  "size": "medium",
  "quantity": 2,
  "customer_name": "Ирина",
  "status": "pending",
  "created_at": "2026-07-10T09:15:00"
}
```

**Частичное обновление статуса.** Запрос:

```http
PATCH /orders/1

{
  "status": "ready"
}
```

Ответ (статус 200): тот же заказ, но с `"status": "ready"` и без изменений в остальных полях, включая `created_at`. Эта метка времени фиксирует момент создания заказа и не должна меняться при обновлении.
